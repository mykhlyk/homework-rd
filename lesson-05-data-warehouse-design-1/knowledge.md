# Заняття 05. Проєктування сховищ даних. Частина 1: огляд та архітектура

## Навіщо це заняття

Уяви, що ти — розробник, якому треба відповісти на два питання одночасно: «скільки поїздок сьогодні зробив водій Іван?» і «яка загальна виручка за всі поїздки у Манхеттені за перший квартал 2024 року?». Перше питання вимагає однієї швидкої точкової операції — типово для операційних систем (OLTP). Друге вимагає сканування мільйонів рядків, агрегацій, групувань — типово для аналітики (OLAP). Якщо намагатись відповідати на обидва типи запитів з однієї бази, ти отримаєш або повільну аналітику, або заблоковані операційні транзакції. З цього конфлікту виростає окрема архітектура — **сховище даних (Data Warehouse, DWH)**.

У цьому занятті ми закладаємо архітектурний фундамент усієї платформи курсу. Ти дізнаєшся, що таке DWH за класичними визначеннями, познайомишся з двома головними школами його побудови (Inmon і Kimball), і — найголовніше — самостійно спроєктуєш і матеріалізуєш повноцінний **Gold-шар** для NYC Taxi в dbt-на-DuckDB. Це перший момент у курсі, коли дані проходять весь шлях: з сирого Parquet-файлу аж до готової аналітичної структури зі star schema, 6 вимірами і таблицею фактів із ~2.9 мільйонами рядків.

Після цього заняття ти зможеш пояснити різницю між OLTP і OLAP, застосувати Kimball 4-step process до будь-якого бізнес-процесу, обрати між star schema, snowflake та OBT, а також написати dbt-модель, де факт join-иться до вимірів зі surrogate key і COALESCE-захисним «Unknown».

## Operational vs Analytical queries: де корінь проблеми

Перш ніж говорити про будь-яку архітектуру, варто глибоко зрозуміти проблему, яку вона вирішує. Уся ця різниця між OLTP і OLAP — не академічна тонкість, а щоденна реальність кожного Data Engineer-а.

### OLTP-запити: точковість і швидкість

Операційна система (наприклад, застосунок для виклику таксі) постійно вносить дрібні зміни стану:

```sql
INSERT INTO trips (trip_id, passenger_id, driver_id, start_time, status)
VALUES (12345, 67890, 54321, CURRENT_TIMESTAMP, 'in_progress');
```

Такий запит торкається одного-двох рядків, виконується за мілісекунди, і водночас його можуть виконувати тисячі водіїв. Оптимізація OLTP-системи — це мінімальний час відповіді на точкові зміни при максимальній конкурентності. Дані зберігаються нормалізовано (щоб оновлення в одному місці проходило без дублювання), індекси налаштовані під WHERE по первинних ключах.

### OLAP-запити: масштаб і агрегації

Аналітик хоче зовсім інше:

```sql
SELECT driver_id,
       SUM(amount) AS total_earnings,
       COUNT(*)    AS total_trips
FROM trips t
JOIN payments p ON t.trip_id = p.trip_id
WHERE t.start_time >= '2025-01-01'
  AND t.start_time <= '2025-03-31'
GROUP BY driver_id
ORDER BY total_earnings DESC;
```

Цей запит сканує мільйони рядків, агрегує, сортує, і повертає зведену таблицю. Тут важлива не швидкість однієї транзакції, а пропускна здатність при читанні великих обсягів. Нормалізація заважає — вона примножує JOIN-и. Натомість потрібні колонкове зберігання, компресія, партиціювання, і денормалізація для зменшення кількості з'єднань.

Один рушій **не може бути одночасно оптимальним для обох режимів**. Це і є головна мотивація для окремого аналітичного сховища з власною схемою зберігання.

### Дані мають форму: формати, стискання, кодування

Аналітичне сховище також змушує свідомо думати про представлення даних. Кілька понять, які варто тримати в голові:

- **Тип даних:** структуровані (таблиці), напівструктуровані (JSON, CSV), неструктуровані (текст, медіа).
- **Формати зберігання:** CSV/JSON — рядкові, людиночитні, зручні для обміну, але неефективні для аналітики. Parquet — колонковий бінарний формат: зберігає дані по колонках, що дозволяє читати лише потрібні стовпці і добре стискатись.
- **Стискання (compression):** lossless-алгоритми (gzip, snappy, zstd) зменшують розмір файлу без втрати даних — саме вони для аналітичних даних. Lossy (JPEG) — лише для медіа.
- **Кодування (encoding):** RLE (run-length encoding) стискає послідовності однакових значень (наприклад, сотні рядків з `vendor_id = 1`); Delta encoding — різниці між послідовними числами. Ці техніки вбудовані у Parquet.
- **Шифрування:** захист конфіденційних даних (PII, фінансові дані) через симетричне або асиметричне шифрування.

Без свідомого вибору формату і схеми сховище перетворюється на хаос — ніхто не знає одиниць виміру, несумісні типи, мільйони дублікатів.

## Визначення та характеристики DWH

### Класичне визначення (Gartner)

Data Warehouse — це архітектура зберігання, призначена для зберігання даних, витягнутих із транзакційних систем, операційних сховищ і зовнішніх джерел, та об'єднання їх у формі, придатній для аналізу і звітності по заздалегідь визначених бізнес-потребах.

Це означає, що DWH — **не просто велика база даних**. Це архітектурне рішення, спрямоване на аналіз, а не на запис транзакцій.

### Чотири характеристики (Inmon)

Білл Інмон, якого вважають «батьком DWH», сформулював чотири ключові характеристики:

**Subject-oriented** — дані організовані навколо предметних областей (клієнти, поїздки, платежі), а не навколо функцій застосунків (бухгалтерія, логістика). Замість таблиці «транзакції Airbnb-сервісу» — таблиця «бронювання», де зібрані всі дані про бронювання з різних систем.

**Time-variant** — кожен запис прив'язаний до конкретного моменту часу. У OLTP-системі зазвичай зберігається поточний стан (що зараз). У DWH зберігається весь часовий ряд — можна побачити, яким був стан на будь-яку дату в минулому.

**Non-volatile** — записи не оновлюються в нормальному процесі (на відміну від OLTP, де UPDATE — буденна операція). Нові дані **додаються**, а не перезаписують старі. Це гарантує стабільність аналітичних результатів.

**Historical** — DWH накопичує великий обсяг історичних даних (місяці, роки), тоді як OLTP зазвичай тримає лише поточний знімок.

## Дві школи: Inmon vs Kimball

У проєктуванні DWH існують дві канонічні школи, і вибір між ними визначає весь архітектурний підхід.

### Inmon: top-down, нормалізований EDW

Білл Інмон пропонує починати зверху: спочатку побудувати **нормалізований (3NF) Enterprise Data Warehouse** — єдине централізоване сховище всієї компанії. З нього вже «нарізаються» тематичні вітрини (data marts) для аналітиків конкретних підрозділів.

Переваги: одна версія правди для всієї компанії, відсутність дублювання, консистентність. Недоліки: складний і тривалий початковий дизайн, перш ніж аналітики отримають щось корисне.

### Kimball: bottom-up, dimensional modeling

Ральф Кімбол іде знизу вгору: спершу — data mart для конкретного бізнес-процесу, з денормалізованою star schema. Ці marts конструюються так, щоб shared dimensions були сумісними між собою (bus matrix).

Переваги: швидко дати аналітикам корисний результат, зрозуміла структура для запитів типу GROUP BY. Недоліки: при погано спроєктованих shared dimensions різні marts можуть давати суперечливі результати.

**Наша платформа будується за Кіммболом.** Аргумент простий: наші головні споживачі — аналітики, яким потрібен ad-hoc `GROUP BY`, а для цього денормалізовані dimension-таблиці (менше JOIN) зручніші, ніж нормалізований EDW.

### Денормалізація: що це означає на практиці

Нормалізована (3NF) модель розносить дані по багатьох таблицях, щоб уникнути дублювання. Наприклад, назва зони та назва боро зберігаються окремо від поїздок. Щоб дізнатись, у якому боро відбувся pickup, треба зробити JOIN через кілька таблиць.

Денормалізація **свідомо повторює** описові атрибути. У dimension `gld_dim_location` одразу є і `zone_name`, і `borough` — ціною того, що якщо NYC перейменує боро, треба оновити багато рядків. В OLAP-сховищі це вирішується через SCD (Slowly Changing Dimensions), а не нормалізацію.

## Kimball 4-step process

Перед тим як малювати таблиці та колонки, Кімбол пропонує пройти чотири кроки **у суворому порядку**. Пропустити крок 2 — типова помилка, яка призводить до невірних агрегацій.

### Крок 1: Обрати business process

Не «департамент», не «система» — а конкретна **бізнес-подія**, що генерує виміри. У нас: завершена поїздка NYC Yellow Taxi. Аналіз поїздок і виручки — це один business process.

### Крок 2: Оголосити grain

Grain — це **одне речення**, що описує, що означає один рядок у fact table. «Один рядок `gld_fact_trip` = одна завершена поїздка» — ось grain.

Чому це так важливо? Бо grain фіксує все подальше. Якщо ти почнеш без явного grain, частина рядків буде поїздками, частина — платежами, і `SUM(fare_amount)` почне подвоювати суми без жодного повідомлення про помилку. Завжди оголошуй grain другим кроком.

### Крок 3: Обрати dimensions

Dimensions — це все, що ми **знаємо про подію**: хто, що, де, коли. Для поїздки:
- **Коли:** дата (pickup і dropoff) та час доби
- **Де:** зона посадки і висадки
- **Як платили:** тип оплати
- **За яким тарифом:** rate code
- **Який вендор:** компанія-постачальник таксі

### Крок 4: Обрати facts

Facts — це **числові вимірювані величини**, які агрегуються по dimensions. Для поїздки: `fare_amount`, `tip_amount`, `tolls_amount`, `total_amount`, `trip_distance`, `duration_sec`, `passenger_count`. Усі вони **additive** на нашому grain — їх можна складати між різними поїздками, і результат матиме сенс.

## Star Schema, Snowflake Schema, OBT і Data Marts

Це чотири архітектурні рішення, які треба вміти розрізняти і свідомо обирати між ними.

### Star Schema: центр і промені

Star schema виглядає наступним чином:

```
          gld_dim_date
               │
gld_dim_vendor ┼── gld_fact_trip ──┬── gld_dim_location (pickup)
               │                   └── gld_dim_location (dropoff)
        gld_dim_payment_type
```

У центрі — **fact table** із числовими мірами і зовнішніми ключами (FK) до dimension tables. Навколо — **dimension tables** із описовими атрибутами (хто, що, де, коли). Dimensions **денормалізовані**: наприклад, `gld_dim_location` містить і назву зони, і назву боро в одному рядку, без окремої таблиці для боро.

Переваги:
- Прості JOIN (fact + потрібні dims)
- Зрозуміло аналітикам
- Добре для BI-інструментів

Недоліки:
- Денормалізація — більше дискового простору
- При зміні описових атрибутів (наприклад, перейменування зони) треба оновити dimension (вирішується SCD)

### Snowflake Schema: нормалізований star

Snowflake відрізняється тим, що dimensions також нормалізовані: наприклад, `borough` виноситься в окрему таблицю, і `gld_dim_location` посилається на неї. Менше дублювання — але більше JOIN при запитах.

На практиці Data Engineer-и майже завжди обирають **star для аналітики**, оскільки productivность аналітиків важливіша за збереження кількох відсотків дискового простору.

### OBT (One Big Table): усе в одній таблиці

Протилежний полюс від star: всі атрибути всіх dimensions «вкладені» прямо в рядок факту. Жодного JOIN при запиті. Широка таблиця на 40–80 колонок.

У колонковій епосі (DuckDB, ClickHouse) це реальна альтернатива: колонкові рушії добре стискають широкі таблиці і читають лише потрібні колонки. Питання «а чи потрібен star, чи достатньо OBT?» — не риторичне.

У нашій платформі ми тримаємо обидва: `gld_fact_trip` + 6 dims — це star (нормалізована форма, одне джерело правди для кожного виміру); `gld_trip_enriched` — OBT, побудований *з* star, не замість неї. Star використовується для підтримки і еволюції даних; OBT — для BI-вітрин без JOIN.

### Data Marts: тематичні вітрини

Gold-шар у Kimball-підході — це набір **data marts**. Кожен mart відповідає на питання одного business process. Наприклад, `gld_zone_revenue` — виручка по зонах NYC. Marts share конформні dimensions (тобто `gld_dim_location` використовується і в `gld_fact_trip`, і в іншому можливому mart-і по зонах).

## Star Schema для NYC Taxi: деталі реалізації

### Fact table: `gld_fact_trip`

Один рядок = одна завершена поїздка. Усі числові міри — additive. Таблиця будується зі `slr_yellow_trips` і join-иться до кожного виміру для резолвінгу surrogate key.

| Колонка | Призначення |
|---|---|
| `trip_sk` | Surrogate key (primary key) |
| `pickup_date_key`, `dropoff_date_key` | FK → `gld_dim_date` |
| `pickup_time_key` | FK → `gld_dim_time` |
| `pu_location_key`, `do_location_key` | FK → `gld_dim_location` (SCD2) |
| `vendor_key` | FK → `gld_dim_vendor` |
| `rate_code_key` | FK → `gld_dim_rate_code` |
| `payment_type_key` | FK → `gld_dim_payment_type` |
| `fare_amount`, `tip_amount` … `total_amount` | Additive міри (DECIMAL) |
| `trip_distance` | Відстань (DOUBLE) |
| `duration_sec` | Тривалість поїздки в секундах (BIGINT) |
| `passenger_count` | Кількість пасажирів (SMALLINT) |

### Surrogate key: навіщо md5?

`trip_sk` — синтетичний ключ, згенерований як `md5()` від природного ключа (6 колонок: `pickup_datetime + dropoff_datetime + pu_location_id + do_location_id + fare_amount + total_amount`). Чому 6 колонок, а не менше? Бо якщо взяти лише 3-4, виникають колізії — ~3800 рядків мають однаковий узкий ключ і стають неунікальними.

Чому `md5()`, а не serial integer? Тому що `md5` є **детермінованим**: той самий набір значень завжди дає той самий хеш, незалежно від того, скільки разів запускаєш і в якому середовищі. Serial integer вимагає координації між паралельними запусками. Той самий підхід pracює в DuckDB і в Spark — це важливо для уроку 12.

### Role-playing dimensions

`gld_dim_location` приєднується до fact table **двічі**: один раз для pickup зони, другий — для dropoff. Це називається **role-playing dimension**: одна фізична таблиця, але два логічні alias-и. Те саме — `gld_dim_date` (pickup date і dropoff date).

### Dimension: `gld_dim_date`

Calendar dimension, згенерована рекурсивним CTE (немає реального джерела — лише математика дат), охоплює 2009-01-01 по 2030-12-31:

```
date_key (YYYYMMDD INT PK), full_date, year, quarter, month, month_name,
day, day_of_week, day_name, is_weekend
```

### Dimension: `gld_dim_time`

Time-of-day dimension, 1440 рядків (одна хвилина = один рядок):

```
time_key (HHMM INT PK), hour, minute, time_of_day, is_rush_hour (07-09, 16-18)
```

**Важлива пастка:** у DuckDB символ `/` — це float-division. Вираз `510/60*100` дає `880.0`, а не `830`. Для коректного `time_key` потрібна цілочисельна ділення `//`, інакше ключ буде некоректним — і JOIN до факту тихо не сходитиметься (NULL без жодного повідомлення про помилку).

### Lookup dimensions через seed

Невеликі домени (vendor, rate_code, payment_type) ведуться як **CSV-seeds у репозиторії** і через dbt завантажуються в таблиці. Чому seed, а не `VALUES` у SQL-моделі?

- Домен редагується як CSV-файл (git diff, зрозумілий навіть не-інженеру)
- Додати нове значення (наприклад, vendor 6 або payment 0) — це один рядок у файлі, а не правка SQL
- Кожен вимір має рядок `-1 / Unknown` — критичний захист від «orphan FK»: якщо в поїздці `vendor_id` NULL або невідомий, COALESCE підставить `-1`, і FK завжди вказуватиме на наявний рядок

### Bus Matrix

Kimball-концепт, що показує, які dimensions share між fact tables:

| | gld_dim_location | gld_dim_date | gld_dim_time | gld_dim_rate_code | gld_dim_payment_type | gld_dim_vendor |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| gld_fact_trip | ✓✓ | ✓✓ | ✓ | ✓ | ✓ | ✓ |

(✓✓ = два FK: pickup і dropoff — role-playing dimension)

### OBT: `gld_trip_enriched`

Star «розплющена» в одну широку таблицю: `gld_fact_trip` + всі атрибути з шести dimensions. Запит без жодного JOIN — для BI-вітрин і дашбордів. Будується після того, як star вже матеріалізована.

## Medallion Architecture: шари зростаючої якості

Medallion — це архітектурний патерн для організації даних у шари з наростаючою якістю. Важливо розуміти: **Medallion — це плумбінг pipeline, а не частина Kimball-дизайну**. Це два незалежних концепти, які гарно поєднуються.

```
source (remote Parquet через on-run-start hook)
    ↓
brz_  Bronze  — typed copy, raw (1:1 дзеркало, лише типізація)
    ↓
slr_  Silver  — cleaned, validated (DQ-фільтри: NULL у PK, від'ємні числа)
    ↓
gld_  Gold    — star schema + OBT + marts (business-ready)

seed_*  — raw reference CSV (довідники)
```

**Landing ≠ Bronze ≠ Silver** — три різні семантики:
- **Landing:** некерований immutable файловий дроп (raw файл, як він є з джерела)
- **Bronze:** керований шар із типізованою схемою і явною семантикою
- **Silver:** очищені дані (пройшли DQ-перевірки)

У нашому demo роль landing виконує remote Parquet, який `on-run-start` hook загортає у view `yellow_trips_raw` до старту будь-якої моделі.

## Gold-шар у dbt: як виглядає код

Ось ключовий фрагмент моделі `gld_fact_trip` — вона показує одночасно кілька концепцій: surrogate key через md5, role-playing dimension join, COALESCE для Unknown member:

```sql
-- models/gold/gld_fact_trip.sql
{{ config(materialized='table') }}

WITH trips AS (
    SELECT *,
        CAST(STRFTIME(tpep_pickup_datetime, '%Y%m%d') AS INTEGER) AS pickup_date_id,
        CAST(STRFTIME(tpep_pickup_datetime, '%H%M')   AS INTEGER) AS pickup_time_id
    FROM {{ ref('slr_yellow_trips') }}
)
SELECT
    md5(
        t.tpep_pickup_datetime::VARCHAR  || '|' || t.tpep_dropoff_datetime::VARCHAR
        || '|' || t.pu_location_id::VARCHAR || '|' || t.do_location_id::VARCHAR
        || '|' || t.fare_amount::VARCHAR    || '|' || t.total_amount::VARCHAR
    )                                  AS trip_sk,
    ddp.date_key                       AS pickup_date_key,
    pu.location_key                    AS pu_location_key,        -- SCD2 surrogate
    COALESCE(dv.vendor_id, -1)         AS vendor_key,             -- unmatched → Unknown
    t.fare_amount, t.tip_amount, t.total_amount,
    DATEDIFF('second', t.tpep_pickup_datetime, t.tpep_dropoff_datetime)::BIGINT AS duration_sec
FROM trips t
LEFT JOIN {{ ref('gld_dim_location') }} pu ON t.pu_location_id = pu.location_id AND pu.is_current
LEFT JOIN {{ ref('gld_dim_date') }} ddp ON ddp.date_key = t.pickup_date_id
LEFT JOIN {{ ref('gld_dim_vendor') }} dv ON dv.vendor_id = COALESCE(t.vendor_id, -1)
```

Зверни увагу: факт **явно join-иться до кожного виміру**. Це не просто копіювання ключів — цей join є єдиним, що створює ребра в lineage-графі dbt (`dbt docs`). Без join-ів виміри «висіли б» у графі без зв'язку з фактом.

### Тонка lookup-dimension зі seed

```sql
-- models/gold/gld_dim_vendor.sql
{{ config(materialized='table') }}
SELECT CAST(vendor_id AS INTEGER) AS vendor_id, vendor_name
FROM {{ ref('seed_vendor') }}
```

Ця модель буквально передає seed у типізовану таблицю. Уся логіка vendor — у CSV-файлі, а модель лише типізує.

### schema.yml — data contract для Gold

```yaml
models:
  - name: gld_fact_trip
    columns:
      - name: trip_sk
        tests: [not_null, unique]
      - name: pu_location_key
        tests:
          - relationships: { to: ref('gld_dim_location'), field: location_key }
      - name: vendor_key
        tests:
          - relationships: { to: ref('gld_dim_vendor'), field: vendor_id }
```

`not_null` + `unique` на `trip_sk` гарантує grain. `relationships`-тест перевіряє referential integrity — кожен FK у факті існує у відповідному вимірі. Цей тест є **data contract**: явна гарантія якості, задокументована у коді.

### Запуск: `dbt build`

`dbt build` = `dbt seed` + `dbt run` + `dbt test` одним DAG-ом. Очікуваний результат: `PASS=47` (4 seeds + 11 models + 32 tests). Тести виконуються одразу після кожної моделі. Lineage можна подивитись через `dbt docs generate && dbt docs serve`: побачиш `seed_* → gld_dim_*` і `source → brz_ → slr_ → gld_fact_trip → gld_trip_enriched`.

## Ключові терміни

| Термін | Визначення |
|---|---|
| **Operational query** | Точковий UPSERT у OLTP-системі: низька латентність, висока конкурентність, торкається кількох рядків. |
| **Analytical query** | SELECT-сканування з агрегаціями по великих діапазонах (OLAP); читає мільйони рядків. |
| **DWH (Data Warehouse)** | Аналітичне сховище з чотирма характеристиками Інмона: subject-oriented, time-variant, non-volatile, historical. |
| **Inmon** | Top-down підхід: спочатку нормалізований (3NF) Enterprise DWH, потім data marts. |
| **Kimball** | Bottom-up підхід: star schema, data mart per business process. |
| **Dimensional modeling** | Kimball-підхід: моделювання навколо фактів (числові міри) і вимірів (описові атрибути). |
| **Denormalization** | Свідоме дублювання атрибутів у одній таблиці заради простоти і швидкості аналітичних запитів. |
| **Grain** | Одне речення, що описує, що означає один рядок у fact table. Оголошується другим кроком Kimball 4-step. |
| **Star Schema** | Fact table у центрі + денормалізовані dimension tables навколо (як промені зірки). |
| **Snowflake Schema** | Нормалізований star — dimensions мають sub-dimensions, більше JOIN при запитах. |
| **OBT (One Big Table)** | Повністю денормалізована широка таблиця; атрибути всіх вимірів вкладені у рядок факту. |
| **Data Mart** | Тематична аналітична вітрина для одного business process (= Gold-шар у Kimball). |
| **Fact table** | Таблиця з числовими additive-мірами і зовнішніми ключами до вимірів. |
| **Dimension table** | Описова таблиця (хто, що, де, коли): атрибути події. |
| **Surrogate key** | Синтетичний PK (тут — md5 від natural key), незалежний від бізнес-ключів джерела. |
| **Natural key** | Бізнес-ключ із джерела; має унікально ідентифікувати grain (тут — 6 колонок). |
| **Role-playing dimension** | Один вимір, що використовується у fact table кілька разів із різними aliases (pickup / dropoff). |
| **Bus Matrix** | Kimball: таблиця показує, які dimensions shared між fact tables — основа для конформних dimensions. |
| **SCD Type 1** | Overwrite: при зміні атрибуту старе значення затирається. Без history. |
| **SCD Type 2** | New row: при зміні атрибуту старий рядок expire-иться, додається новий. Повна history. |
| **Medallion Architecture** | Шарова архітектура: Bronze (raw) → Silver (cleaned) → Gold (business-ready). |
| **Seed** | CSV-довідник у dbt-репозиторії, який завантажується командою `dbt seed`. |
| **Data Contract** | dbt `schema.yml` як технічна угода: схема + DQ-гарантії (тести). |
| **Data Lineage** | Граф залежностей трансформацій (автоматичний у `dbt docs`). |
