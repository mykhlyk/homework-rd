## Основний матеріал

### 1. Розподілені системи: теоретичні основи

#### 1.1 Паралельні vs розподілені обчислення: у чому різниця

Уявіть офіс. Якщо всі співробітники сидять в одному просторому кабінеті і можуть вільно переговорити між собою або підійти до спільного шафи з документами — це **parallel computing**. Усі ядра одного сервера мають доступ до **спільної пам'яті (shared memory)**: будь-яке ядро може прочитати або записати будь-яку ділянку RAM без складних протоколів. Один сервер, багато ядер.

Тепер уявіть, що ваша команда розкидана по різних містах. Щоб передати колезі документ, потрібно надіслати email або зателефонувати. У кожного є свій стіл, своя папка з паперами, і прямого доступу до чужих матеріалів немає. Це **distributed computing**: кожен вузол (node) має **власну приватну пам'ять (distributed memory)**, а спілкуються вузли через **передачу повідомлень (message passing)** по мережі.

Ця різниця — не просто технічна деталь. Вона фундаментально змінює те, як ви думаєте про стан системи. У shared-memory системі «хто останній записав — той і правий». У distributed системі немає гарантії, що два вузли бачать одні й ті самі дані в один момент часу: мережа може затримати повідомлення, пакет може загубитися.

**Чому взагалі розподілені системи?** Одна машина має фізичні межі: скільки б RAM або SSD ви не встановили, цей ліміт існує. Коли датасет не влазить в одну машину або вимоги до throughput перевищують її можливості, є два шляхи:

- **Scale-up (вертикальне масштабування):** купити потужнішу машину з більшим RAM. Але рано чи пізно ви досягнете технічної або бюджетної стелі.
- **Scale-out (горизонтальне масштабування):** додати більше звичайних (commodity) машин. Дешевше, нескінченно масштабується — але набагато складніше з точки зору узгодженості даних і відмовостійкості.

#### 1.2 Архітектури розподілених систем

Розподілені системи бувають кількох типів, і знання їх допомагає розуміти, чому конкретний продукт влаштований саме так.

**Клієнт-сервер (client-server):** є центральний сервер, який обслуговує клієнтів. Проста модель, але сервер — це single point of failure (якщо він впав — система недоступна) і bottleneck (усі запити через нього).

**Peer-to-peer (P2P):** всі вузли рівноправні, немає виділеного центру. BitTorrent — класичний приклад: файл не лежить на одному сервері, а розподілений між мільйонами учасників. Блокчейн — теж P2P. Дуже стійкі до відмов окремих вузлів, але складніше підтримувати консистентність.

**Cluster і Grid:** cluster — однорідна група пов'язаних машин в одному датацентрі, що працює як єдиний обчислювальний ресурс (Hadoop-кластер — приклад). Grid — гетерогенні машини, можливо в різних географічних локаціях.

**Cloud Computing:** ви орендуєте обчислення і сховище у провайдера (AWS, Azure, GCP) на вимогу. Немає потреби купувати залізо — але є залежність від провайдера і мережевий overhead.

Для обміну між компонентами розподіленої системи використовуються різні моделі: message passing (вузли надсилають один одному пакети), publish/subscribe (одні компоненти публікують події, інші підписуються — ми побачимо це в занятті 16 на Kafka), remote procedure call (RPC — виклик функції на іншому вузлі так, ніби вона локальна).

#### 1.3 ACID: що ми звикли очікувати від бази даних

Перш ніж розбирати CAP-теорему, варто згадати ACID — набір гарантій, які дають класичні реляційні БД.

- **Atomicity (атомарність):** транзакція або виконується повністю, або не виконується взагалі. Якщо ви переказуєте гроші між рахунками і щось пішло не так після дебету, але до кредиту — система відкотиться, гроші не зникнуть.
- **Consistency (узгодженість):** після транзакції БД перебуває в валідному стані. Усі правила цілісності (unique constraints, foreign keys) дотримані.
- **Isolation (ізоляція):** транзакції не заважають одна одній. Ви не бачите «напівзавершених» змін від паралельних транзакцій. Реалізується через блокування (locks) або MVCC (multi-version concurrency control).
- **Durability (стійкість):** після commit зміни зберігаються навіть якщо система впаде одразу після цього.

У PostgreSQL чи MySQL ці гарантії ви отримуєте «безкоштовно». Але в розподіленій системі, де дані розкидані по десятках вузлів, а мережа ненадійна, гарантувати повний ACID на всіх вузлах одночасно надзвичайно дорого. Саме тут виникає CAP.

#### 1.4 CAP-теорема: фундаментальний trade-off розподілених систем

CAP-теорему сформулював Ерік Брюер наприкінці 1990-х (доведено Гілбертом і Лінчем у 2002). Вона говорить: **розподілена система не може одночасно гарантувати всі три властивості**:

- **C — Consistency (узгодженість):** кожне читання повертає найсвіжіший запис або помилку. Якщо вузол A щойно записав нове значення, будь-який вузол B, що читає одразу після цього, отримає саме це нове значення — або відмову.
- **A — Availability (доступність):** кожен запит отримує відповідь (без помилки) — але без гарантії, що дані найсвіжіші.
- **P — Partition Tolerance (стійкість до розділення):** система продовжує працювати, навіть якщо мережа між вузлами дала збій і частина повідомлень загубилася або затрималася.

**Чому не можна мати всі три?** Network partition — розрив мережевого зв'язку між вузлами — трапляється в будь-якій реальній розподіленій системі рано чи пізно (проблеми з кабелями, конфігурацією роутерів, навантаженням). Тому відмовитися від P практично неможливо. Реальний вибір — між **CP** і **AP**:

| Вибір | Поведінка при network partition | Приклади |
|---|---|---|
| **CP** | Система відмовляє частині запитів, щоб гарантувати consistency | HBase, ZooKeeper, etcd |
| **AP** | Система відповідає на всі запити, але може повернути застарілі дані | Cassandra, CouchDB, DynamoDB |

**Практичний приклад:** уявіть інтернет-банк. Під час збою мережі між двома датацентрами:
- CP-система скаже клієнту: «Сервіс тимчасово недоступний» — краще, ніж показати неправильний баланс.
- AP-система покаже баланс — але можливо, що він застарілий на кілька секунд.

Для банківських транзакцій правильний вибір — CP. Для лічильника переглядів відео на YouTube — AP цілком прийнятний.

**Як це стосується наших інструментів:**
- Apache Iceberg (заняття 10) обирає consistency: метадані в одному місці, зміни атомарні.
- Kafka (заняття 16): налаштовується — `acks=all` ближче до CP, `acks=1` ближче до AP.

#### 1.5 Linearizability і BASE: два полюси узгодженості

**Linearizability** — найсильніша форма consistency. Якщо клієнт A прочитав значення v2, то будь-який клієнт B, що читає пізніше, отримає v2 або ще новіше. Система веде себе так, ніби вся вона — одна машина з одним значенням у кожний момент часу. Це інтуїтивно зрозуміло, але дорого реалізувати в розподіленій системі: вузлам потрібно постійно координуватися.

**BASE** — протилежний підхід, характерний для AP-систем:
- **Basically Available:** система відповідає на запити з усіх вузлів, навіть якщо дані можуть бути не найсвіжішими.
- **Soft-state:** стан системи може бути «в процесі» — вузли ще не синхронізувались між собою.
- **Eventually consistent (eventual consistency):** якщо припинити нові записи і дати системі час, всі вузли врешті-решт зійдуться до одного значення. «Врешті-решт» — це може бути мілісекунди або секунди залежно від реалізації.

Cassandra — класичний приклад eventual consistency: якщо ви записали дані в один вузол, і одразу прочитали з іншого — є шанс отримати стару версію. Але через певний час обидва вузли покажуть одне й те саме.

**PACELC** — розширення CAP, яке точніше описує реальні системи. CAP говорить лише про поведінку під час partition. PACELC додає: а що відбувається в **нормальному** режимі (without partition)?

- При **P**artition: вибір між **A**vailability і **C**onsistency.
- **E**lse (нормальний режим): вибір між **L**atency і **C**onsistency.

Навіть без збою мережі є trade-off: щоб гарантувати strong consistency, вузли мають дочекатися підтвердження від всіх реплік — це збільшує latency. Менш суворі моделі узгодженості дозволяють відповісти одразу після запису на один вузол.

### 2. Hadoop: екосистема для розподіленої обробки даних

#### 2.1 З чого все почалося: проблема обробки великих даних

Уявіть завдання: є 1 терабайт даних, і вам потрібно підрахувати кількість трипів по кожній зоні. На звичайному ноутбуці з 16 GB RAM весь датасет не влізе, а якщо навіть влізе — обробка буде повільною. Що робити?

Очевидна ідея: розбити задачу на частини і розподілити між багатьма машинами. Але це породжує нові питання:
- Де зберігати дані, якщо вони не влазять на один диск?
- Як паралельно запустити обробку на кількох машинах?
- Що робити, якщо одна з машин зламалася в процесі обробки?
- Як зібрати результати разом?

Hadoop — перша масштабна open-source відповідь на ці питання.

#### 2.2 Коротка історія

**2004 рік:** Джеффрі Дін і Санджай Гхемават з Google публікують статтю «MapReduce: Simplified Data Processing on Large Clusters». Google вже обробляв терабайти даних для пошукового індексу — і вирішив описати підхід, який вони розробили.

**2005 рік:** Даг Каттінг, розробник пошукового движка Nutch, читає цю статтю і розпочинає реалізацію ідей Google у Java. Проєкт отримує назву Hadoop — на честь плюшевого слона сина Каттінга.

**2008 рік:** Hadoop стає top-level проєктом Apache Software Foundation і встановлює рекорд: сортування 1 терабайта даних за 209 секунд на кластері з 910 вузлів. Це підтверджує: горизонтальне масштабування працює.

Навколо Hadoop виросла ціла екосистема: Hive (SQL поверх Hadoop), HBase (NoSQL-БД на HDFS), Pig (мова для data flows), Spark (швидша альтернатива MapReduce), ZooKeeper (координація), Impala, Flume, Sqoop, Oozie.

#### 2.3 Чотири основних компоненти Hadoop

**Hadoop Common** — базові бібліотеки та утиліти, від яких залежать інші модулі. Включає CLI для роботи з файлами.

**HDFS (Hadoop Distributed File System)** — розподілена файлова система. Вирішує питання зберігання.

**Hadoop MapReduce** — фреймворк для паралельної обробки. Вирішує питання обчислень.

**YARN (Yet Another Resource Negotiator, 2012)** — менеджер ресурсів кластера. Відокремлює управління ресурсами від фреймворку виконання.

#### 2.4 HDFS: розподілена файлова система

HDFS вирішує просту, але важливу проблему: як зберігати великі файли, якщо вони не влазять на один диск? І як зробити так, щоб система не зупинилася, якщо один диск або сервер зламається?

**Архітектура HDFS** складається з двох типів вузлів:

**NameNode** — «бібліотекар», що знає, де що лежить. Зберігає namespace (ієрархію директорій і файлів) і block locations (де знаходиться кожен блок кожного файлу). NameNode — critical component: якщо він недоступний, клієнти не знають, де шукати дані. Тому в production розгортають HA (High Availability) конфігурацію: active + standby NameNode, синхронізовані через ZooKeeper.

**DataNode** — «склад», де фізично лежать дані. Кожен DataNode зберігає блоки файлів. Якщо DataNode не надіслав heartbeat NameNode'у протягом певного часу — NameNode вважає його мертвим і починає ре-реплікацію блоків на інші вузли.

**Розбиття на блоки:** файл розбивається на блоки фіксованого розміру (за замовчуванням 128 MB). Блоки — не файли, це логічні одиниці. Кожен блок реплікується на кількох DataNode (за замовчуванням 3 копії). Розміщення реплік rack-aware: не всі три копії в одній стійці серверів — щоб відмова одного rack не призвела до втрати даних.

```
Файл "trips.parquet" (500 MB) розбивається на 4 блоки по 128 MB:
Block 1 → DataNode1, DataNode3, DataNode7   (3 копії на різних серверах)
Block 2 → DataNode2, DataNode5, DataNode1
Block 3 → DataNode4, DataNode6, DataNode3
Block 4 → DataNode1, DataNode2, DataNode8
```

**Ключові властивості HDFS:**
- **Масштабованість:** додаєте нові DataNode — ємність лінійно зростає.
- **Відмовостійкість:** вихід одного DataNode — автоматична ре-реплікація.
- **Write-once-read-many (WORM):** файли не редагуються, лише append або delete. Це спрощує реплікацію, але обмежує застосування.
- **High throughput, не low latency:** HDFS оптимізований для великих послідовних читань (аналітика), а не для random access по байтам (транзакційні БД).

**HDFS vs S3:** Hadoop спочатку проектувався під принцип **data locality** — запускати обчислення там, де лежать дані, а не пересилати дані до обчислень. Якщо дані на HDFS, Spark може запустити задачу прямо на DataNode, де лежить блок — без мережевого трафіку.

Amazon S3 — managed object storage — дешевше і не вимагає підтримки кластера, але дані і обчислення фізично розділені (мережа між S3 і EC2). Сучасний підхід (у тому числі в нашому демо) — зберігати дані в S3, запускати Spark на EMR, читати через **S3A connector**. Data locality жертвується заради managed storage — і в більшості випадків це виправдано: S3 дешевий, надійний, і мережа AWS між S3 і EC2 в одному регіоні досить швидка.

#### 2.5 MapReduce: як це працює

MapReduce — не просто Hadoop-деталь, а фундаментальна парадигма розподіленої обробки. Розуміння її допомагає зрозуміти Spark, бо Spark реалізує ту саму ідею, але швидше.

Ідея проста: якщо задача піддається декомпозиції на незалежні підзадачі «обробити один запис» і потім «зібрати результати по ключу», її можна розпаралелити на сотні машин.

**Три кроки:**

```
Input → [Map] → (key, value) пари → [Shuffle & Sort] → згруповані по ключу → [Reduce] → Output
```

**Map():** функція застосовується до кожного вхідного запису незалежно і повертає одну або кілька пар (key, value). Виконується паралельно на всіх вузлах, де лежать дані. Немає координації між mapper'ами.

**Shuffle & Sort:** Hadoop збирає всі пари з однаковим key на один Reduce-вузол. Це єдиний крок, де відбувається мережевий трафік між вузлами. Дорога операція — саме тут MapReduce повільний.

**Reduce():** для кожного унікального key отримує всі values і агрегує їх (сума, підрахунок, тощо).

**Приклад на NYC Taxi — підрахунок трипів по зонах:**
```
Дані розподілені по 3 вузлах.

Вузол 1 → Map:  (zone=1, trip1) → (1, 1)
                 (zone=2, trip2) → (2, 1)
                 (zone=1, trip3) → (1, 1)

Вузол 2 → Map:  (zone=1, trip4) → (1, 1)
                 (zone=3, trip5) → (3, 1)

Shuffle: всі (1, ...) → Reducer A, всі (2, ...) → Reducer B, всі (3, ...) → Reducer C

Reducer A (zone=1): sum([1,1,1]) → zone 1 = 3
Reducer B (zone=2): sum([1])     → zone 2 = 1
Reducer C (zone=3): sum([1])     → zone 3 = 1
```

**Чому MapReduce застарів?** Кожен крок записує проміжний результат на диск. Для складного pipeline з 10 кроків — це 10 reads і 10 writes з диску. Диск набагато повільніший за RAM. Spark вирішив цю проблему, тримаючи проміжні результати в пам'яті між кроками — і виявився в 10–100 разів швидшим на ітеративних задачах (ML-алгоритми, що роблять багато проходів по даних).

Але **концепція MapReduce жива**: Spark реалізує ту ж парадигму (функції над distributed collection → shuffle → агрегація), просто без disk I/O між кроками.

#### 2.6 YARN: менеджер ресурсів кластера

До 2012 року Hadoop-кластер міг запускати тільки MapReduce. YARN (HADOOP 2.0) змінив це, відокремивши resource management від execution framework.

**Три компоненти:**

**ResourceManager** — глобальний планувальник кластера. Знає, скільки CPU і RAM доступно на кожному вузлі, і вирішує, де запускати які задачі.

**NodeManager** — агент на кожному worker-вузлі. Звітує ResourceManager про наявні ресурси, запускає та зупиняє containers (ізольовані процеси для виконання задач).

**ApplicationMaster** — per-application компонент. Кожна запущена програма (Spark job, MapReduce job) має свого ApplicationMaster, який домовляється з ResourceManager про ресурси і координує виконання своїх задач.

**Значення YARN:** тепер на одному Hadoop-кластері можна запускати Spark, MapReduce, Flink — вони конкурують за ресурси через єдиний ResourceManager. Саме так працює AWS EMR.

#### 2.7 Hadoop у хмарі

Підтримувати власний Hadoop-кластер — серйозна операційна задача: потрібно купити залізо, налаштувати мережу, моніторити вузли, оновлювати Hadoop. Хмарні провайдери пропонують managed-сервіси:

- **AWS EMR (Elastic MapReduce):** провізіонування кластера EC2-машин, автоматичне встановлення Hadoop/Spark/Hive, інтеграція з S3 і Glue. Підтримує Spot Instances для здешевлення. **Саме EMR ми використовуємо в демо.**
- **GCP Dataproc:** managed Spark + Hadoop на Google Cloud.
- **Azure HDInsight:** на базі Hortonworks HDP.

EMR — типовий вибір для AWS-стеку. Кластер запускається за 8–12 хвилин і зупиняється командою — ви платите тільки за час роботи.

### 4. Live Demo: AWS EMR через boto3

#### 4.1 boto3 — Python SDK для AWS

**boto3** — офіційна Python-бібліотека для взаємодії з усіма сервісами AWS. Замість того щоб клікати в консолі AWS, ви пишете Python-код, який можна версіонувати в Git, повторно запускати, параметризувати. Це перший крок до **infrastructure-as-code** — підходу, при якому вся інфраструктура описана кодом, а не ручними кліками (детально в занятті 19).

#### 4.2 Скрипт `setup_emr.py`: що відбувається

Скрипт робить три речі: створює S3 bucket (якщо не існує), створює Glue database, запускає EMR-кластер.

```python
import boto3

REGION = "us-east-1"
BUCKET_NAME = "de-course-taxi-demo"
EMR_NAME = "de-course-taxi-demo"
KEY_PAIR = "de-course-key"  # must pre-exist in your AWS account

emr = boto3.client("emr", region_name=REGION)
s3 = boto3.client("s3", region_name=REGION)
glue = boto3.client("glue", region_name=REGION)

def provision_emr_cluster() -> str:
    response = emr.run_job_flow(
        Name=EMR_NAME,
        ReleaseLabel="emr-7.0.0",
        Applications=[{"Name": "Spark"}, {"Name": "Hive"}, {"Name": "JupyterHub"}],
        Instances={
            "MasterInstanceType": "m5.xlarge",
            "SlaveInstanceType": "m5.xlarge",
            "InstanceCount": 3,  # 1 master + 2 core (HDFS replication factor = 2)
            "Ec2KeyName": KEY_PAIR,
            "KeepJobFlowAliveWhenNoSteps": True,
        },
        LogUri=f"s3://{BUCKET_NAME}/emr-logs/",
        ServiceRole="EMR_DefaultRole",
        JobFlowRole="EMR_EC2_DefaultRole",
        Configurations=[{
            "Classification": "hive-site",
            "Properties": {
                "hive.metastore.client.factory.class":
                    "com.amazonaws.glue.catalog.metastore.AWSGlueDataCatalogHiveClientFactory"
            },
        }],
    )
    cluster_id = response["JobFlowId"]
    waiter = emr.get_waiter("cluster_running")
    waiter.wait(ClusterId=cluster_id, WaiterConfig={"Delay": 30, "MaxAttempts": 30})
    return cluster_id
```

**Що тут важливо розуміти:**
- `ReleaseLabel="emr-7.0.0"` — версія EMR, що включає Spark 3.5 і Hive 3.x.
- `InstanceCount=3` — 1 master (координує) + 2 core (зберігають HDFS-блоки і виконують задачі).
- `KeepJobFlowAliveWhenNoSteps=True` — кластер не завершується після виконання всіх задач, ми зупинимо його вручну через `teardown_emr.py`.
- `hive-site` конфігурація — Hive використовуватиме AWS Glue як metastore замість вбудованого. Завдяки цьому Hive-таблиці, створені в EMR, видимі і в Athena.
- `waiter` — boto3-механізм, що поллить статус кластера кожні 30 секунд, доки кластер не буде готовий (або не вичерпається 30 × 30 секунд = 15 хвилин).

#### 4.3 Завантаження даних у S3

`upload_data.py` бере той самий `yellow_tripdata_2024-01.parquet`, з яким ми працювали в занятті 02, і завантажує його в S3. Це наша **landing zone** у хмарі.

```python
for path in LOCAL_LANDING.glob("yellow_tripdata_*.parquet"):
    key = f"{S3_PREFIX}/{path.name}"
    s3.upload_file(str(path), BUCKET_NAME, key)
```

Ідея continuity: той самий файл — але тепер на managed S3, доступному всьому кластеру.

#### 4.4 Hive external table: зв'язуємо S3 і SQL

Після того як кластер готовий, ми підключаємося до JupyterHub (вбудований ноутбук на EMR) і створюємо Hive **external table** над даними в S3.

```sql
CREATE EXTERNAL TABLE IF NOT EXISTS taxi_bronze.yellow_trips (
    VendorID              BIGINT,
    tpep_pickup_datetime  TIMESTAMP,
    tpep_dropoff_datetime TIMESTAMP,
    passenger_count       BIGINT,
    trip_distance         DOUBLE,
    fare_amount           DOUBLE,
    tip_amount            DOUBLE,
    total_amount          DOUBLE,
    PULocationID          BIGINT,
    DOLocationID          BIGINT
)
STORED AS PARQUET
LOCATION 's3://de-course-taxi-demo/landing/'
```

**Ключове слово EXTERNAL** означає: Hive реєструє таблицю (зберігає схему і location в Glue Catalog), але не переміщує і не «захоплює» файли. Якщо виконати `DROP TABLE` — таблиця зникне з Glue, але Parquet-файли в S3 залишаться. Це принцип **розділення storage і compute**, на якому побудовані сучасні data lake архітектури.

Перший розподілений запит — `COUNT(*)` і `SUM(fare_amount)` над ~2.96 млн рядків. Spark розпаралелює читання між двома core nodes, кожен читає свою частину Parquet з S3.

#### 4.5 YARN у консолі EMR

Поки запит виконується, можна відкрити YARN ResourceManager UI і побачити все наживо:
- **Cluster state: WAITING** — кластер готовий, чекає задач.
- **Applications Running: 1** — наш Spark job.
- **Memory Total** — загальна пам'ять двох core nodes.
- **Node Manager вузли** — два core nodes. Master node не бере участь в обчисленнях (він — координатор).

#### 4.6 Teardown: як не залишити кластер «включеним»

```python
cluster_id = Path(".emr_cluster_id").read_text().strip()
emr.terminate_job_flows(JobFlowIds=[cluster_id])
emr.get_waiter("cluster_terminated").wait(ClusterId=cluster_id)
# S3 bucket and Glue Catalog retained — used in Lesson 10.
```

**ВАЖЛИВО:** teardown зупиняє тільки кластер. S3 bucket `de-course-taxi-demo` і Glue database `taxi_bronze` навмисно залишаються — вони потрібні в занятті 10 (Iceberg на Athena). **Не видаляйте їх після цього заняття.**

### 5. Glue Data Catalog: що це і навіщо

AWS Glue Data Catalog — managed реєстр метаданих, сумісний з API Hive Metastore. Зберігає database definitions, table definitions (схема, location, format), partition metadata.

Завдяки тому, що EMR налаштований на Glue як metastore, Hive-таблиця, створена в EMR, автоматично з'являється в **Athena** — serverless SQL-engine від AWS. І навпаки: таблиці, створені в Athena, доступні в Hive на EMR. Glue Catalog — єдиний catalog для всіх AWS-сервісів.

Це архітектурний місток до заняття 10, де ми створимо Iceberg-таблицю через Athena, використовуючи ту саму інфраструктуру.

### 6. Коли достатньо ноутбука, а коли потрібен кластер

Важливий урок: розподілена система — не самоціль. Вона додає складність і latency. Порівняння:

| | DuckDB (локально) | Spark на EMR |
|---|---|---|
| Scale | Гігабайти, один сервер | Терабайти, сотні вузлів |
| Latency | Мілісекунди | Десятки секунд |
| Вартість | $0 | ~$0.55 / демо |
| SQL | Повний DuckDB SQL | Hive / Spark SQL |

Хороший Data Engineer вміє обрати правильний інструмент для задачі. 50 MB Parquet і одноразовий аналіз? DuckDB на ноутбуці — за 2 секунди. 50 TB даних за рік, щоденний pipeline? EMR або Databricks — єдиний варіант. Починайте з простого і масштабуйте тільки тоді, коли є конкретна причина.

## Ключові терміни

| Термін (English) | Визначення |
|---|---|
| **Distributed system** | Система, де вузли мають власну приватну пам'ять і спілкуються через message passing по мережі. |
| **Parallel computing** | Обчислення з кількома процесорами, що мають спільну пам'ять (shared memory) на одному сервері. |
| **Scale-out / scale-up** | Горизонтальне масштабування (більше машин) проти вертикального (потужніша машина). |
| **ACID** | Набір гарантій транзакцій: Atomicity, Consistency, Isolation, Durability. |
| **CAP Theorem** | Розподілена система одночасно гарантує максимум 2 з 3: Consistency, Availability, Partition Tolerance. |
| **Linearizability** | Найсильніша модель consistency: після читання версії v2 жоден клієнт не прочитає старішу версію. |
| **BASE / eventual consistency** | Basically Available, Soft-state, Eventually consistent — модель AP-систем, протилежна ACID. |
| **PACELC** | Розширення CAP: при Partition — між A і C; інакше (Else) — між Latency і Consistency. |
| **HDFS** | Hadoop Distributed File System: блокова розподілена FS на commodity hardware. Блоки 128 MB, реплікація (default 3). |
| **NameNode** | Сервер метаданих HDFS: зберігає namespace і block locations. |
| **DataNode** | Сервер даних HDFS: фізично зберігає блоки файлів. |
| **MapReduce** | Парадигма паралельної обробки: Map (трансформація) → Shuffle (групування по ключу) → Reduce (агрегація). Disk-based, застарілий. |
| **YARN** | Yet Another Resource Negotiator — менеджер ресурсів Hadoop-кластера. Відокремлює resource management від execution. |
| **Data locality** | Принцип запуску обчислень там, де фізично лежать дані — мінімізує мережевий трафік. |
| **EMR (Elastic MapReduce)** | AWS managed Hadoop/Spark cluster service. |
| **boto3** | Python SDK для AWS. Програмне управління сервісами (infrastructure-as-code). |
| **Hive external table** | Таблиця, чиї дані живуть поза Hive (в S3). DROP TABLE не видаляє дані. |
| **Glue Data Catalog** | AWS managed Hive Metastore — реєстр table definitions для EMR і Athena. |
| **S3A connector** | Інтерфейс, через який Spark/Hadoop читають і пишуть Amazon S3 замість HDFS. |
